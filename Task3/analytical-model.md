# Проектирование целевой аналитической модели данных

В данном документе приведено описание целевой аналитической модели для домена «Анализ транзакций». Модель спроектирована по классической денормализованной схеме **«Звезда» (Star Schema)** для обеспечения максимального быстродействия бизнес-отчетности.

## 1. Структура аналитической модели «Звезда»

### Центр схемы: Таблица фактов (Fact Table)
*   **`fact_transactions`** — Журнал подтвержденных финансовых операций Главной книги и карточного процессинга.
    *   *Метрики (Показатели):* `transaction_amount` (сумма операции), `fee_amount` (сумма комиссии), `currency_rate` (курс конвертации).
    *   *Ключи связей:* `fk_date` (суррогатный ключ даты), `fk_source_customer` (клиент-отправитель), `fk_target_customer` (клиент-получатель), `fk_account_product` (счет и продукт списания), `fk_branch` (отделение ведения счета).

### Лучи схемы: Таблицы измерений (Dimension Tables)
1.  **`dim_customer`** — Единый справочник контрагентов (на основе «золотой записи» MDM).
    *   *Атрибуты:* `unique_id`, `customer_name`, `inn` (для ЮЛ/ФЛ/ИП по требованиям 115-ФЗ), `snils` (уникальный пожизненный идентификатор строго для ФЛ), `customer_type` (ФЛ/ЮЛ), `segment_type` (Масс/VIP/МСБ).
2.  **`dim_calendar`** — Предсчитанный справочник времени для оптимизации вычислений.
    *   *Атрибуты:* `date_key` (в формате YYYYMMDD), `full_date`, `day_of_week`, `week_of_year`, `month_number`, `month_name`, `quarter`, `year`, `is_holiday` (признак выходного/праздничного дня по производственному календарю РФ).
3.  **`dim_account_product`** — Консолидированный справочник счетов и привязанных банковских продуктов.
    *   *Атрибуты:* `account_key`, `account_number` (20-значный балансовый счет), `card_masked_pan`, `product_name` (название тарифа), `product_type` (кредит/дебет/депозит), `product_status`.
4.  **`dim_branch`** — Географическая структура отделений для оценки эффективности слияния.
    *   *Атрибуты:* `branch_key`, `branch_name`, `branch_type` (доп. офис/ККО), `city`, `region`, `macro_region`.

## 2. Обоснование выбора схемы «Звезда» и состава полей для OLAP

Выбор структуры и состава атрибутов обусловлен жесткими требованиями к производительности при обработке больших данных (OLAP) и банковской спецификой:

1.  **Экономия CPU за счет суррогатного ключа даты (`fk_date`):** Использование предсчитанного справочника `dim_calendar` вместо динамического парсинга полей `timestamp` исключает ресурсоемкие вычисления функций `EXTRACT` или `DATE_TRUNC` на миллиардах строк. Группировки по неделям, кварталам и производственным праздникам выполняются через мгновенный хэш-индекс по числу формата YYYYMMDD, разгружая процессоры Trino.
2.  **Географический анализ эффективности слияния (`fk_branch`):** Наличие выделенного ключа отделения привязано к офису ведения счета отправителя. Это критически необходимо Финансовому департаменту для проведения `Drill-Down` анализа прибыльности конкретных точек присутствия поглощенного банка, отслеживания миграции локальных клиентов и оценки окупаемости филиальной сети To-Be.
3.  **Гибридная идентификация контрагентов (ИНН и СНИЛС):** Хранение обоих полей в `dim_customer` обусловлено тем, что СНИЛС является идеальным сквозным идентификатором для физических лиц (не меняется при смене паспорта), но полностью отсутствует у юридических лиц. Поле ИНН присутствует у всех типов клиентов и является обязательным для выполнения комплаенс-проверок по 115-ФЗ и выгрузки отчетности в налоговые органы. Наличие обоих полей позволяет MDM использовать резервные правила сопоставления при пропусках данных в legacy-системах.
4.  **Минимизация каскадных соединений (JOIN):** Денормализация справочника отделений (иерархия офис-город-регион в одной строке) и справочника продуктов позволяет BI-системе строить аналитические дашборды через плоские одноуровневые соединения с таблицей фактов, обеспечивая комфортный отклик интерфейса для топ-менеджмента при работе с петабайтными массивами.
