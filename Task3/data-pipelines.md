# Проектирование пайплайнов данных (Data Pipelines)

В данном документе приведено описание ключевых пайплайнов данных для промежуточного и целевого состояний аналитической платформы объединенного банка.

---

## 1. Реестр целевых и промежуточных пайплайнов данных

### Пайплайн 1: Репликация и очистка клиентских профилей (MVP, 3 месяца)
*   **Источник данных:** CRM FinUnion и CRM RetailBank [1.1].
*   **Характер данных:** Исторические / Изменяемые (анкетные данные клиентов и сотрудников) [1.1].
*   **Целевое хранилище:** Классическое DWH на PostgreSQL (Слой Staging) ➔ Модуль MDM Customer Hub [1.1].
*   **Способ обработки:** Асинхронный, **Daily Batch** (Ночной запуск через Airflow). Для поглощаемого банка применяется CDC (Debezium) для снижения нагрузки на legacy-базу [1.1].
*   **Потребители:** Финансовый департамент, Риск-менеджмент, Бизнес-витрины BI (для утренней отчетности) [1.1].
*   **Архитектурная логика (Трансформация):** Применяется гибридный подход **ETL/ELT**. Данные CRM копируются один в один в Staging-слой DWH (ELT), параллельно анкеты уходят в MDM-модуль, где проходят форматно-логический контроль (Validate), дедупликацию по СНИЛС/паспорту и обогащаются (Enrich) сквозным UniqueID [1.1].

### Пайплайн 2: Обработка истории карточных операций (Target, 12 месяцев)
*   **Источник данных:** Единый карточный процессинг объединенного банка [1.1].
*   **Характер данных:** Событийные (непрерывный высокоинтенсивный поток финансовых транзакций) [1.1].
*   **Целевое хранилище:** **Data Lakehouse** (Объектное хранилище S3 в табличном формате Apache Iceberg) [1.1].
*   **Способ обработки:** Асинхронный, **Hourly/Daily Batch** (Пакетная дозапись новых строк через Airflow в технологические окна) [1.1].
*   **Потребители:** Риск-менеджмент (расчет долговой нагрузки), Служба безопасности и Комплаенс (проведение расследований), BI [1.1].
*   **Архитектурная логика (Трансформация):** Данные транзакций сохраняются в файлы формата Parquet под управлением Apache Iceberg. За счет партиционирования таблиц Iceberg по датам и индексации по ID клиентов, Служба безопасности может мгновенно с помощью движка **Trino** выгружать историю платежей любого фигуранта за 5 лет для выявления подельников, считывая только нужные файлы с S3 без перебора всего петабайтного массива [1.1].

### Пайплайн 3: Миграция архивных выгрузок поглощаемого банка (Target, 12 месяцев)
*   **Источник данных:** Legacy-базы отключенных систем RetailBank (счета, старые кредиты, логи АБС) [1.1].
*   **Характер данных:** Архивные (статичные исторические срезы мертвых систем на момент слияния) [1.1].
*   **Целевое хранилище:** **Data Lakehouse** (Дешевая зона архива на S3 в формате Apache Iceberg) [1.1].
*   **Способ обработки:** Асинхронный, **One-time / Серийный Batch** (крупные пакетные загрузки строго в ночное время с минимальной нагрузкой на сеть) [1.1].
*   **Потребители:** Команда моделей Data Science (обучение ИИ и прогнозирование), Аудиторы, ЦБ РФ [1.1].
*   **Архитектурная логика (Трансформация):** Источники данных больше не изменяются. Данные мигрируют один раз. Хранение организовано в экономичном слое Lakehouse, что позволяет банку не тратить бюджет на дорогие лицензии СУБД, но сохранять данные 5 лет по закону. Наличие этих архивов позволяет моделям ИИ обучаться на долгой истории поведения клиентов для точного прогнозирования оттока и кросс-продаж [1.1].

### Пайплайн 4: Сбор событий клиентских каналов (Target, 12 месяцев)
*   **Источник данных:** Логи кликстрима (Кликстрим мобильного приложения и интернет-банка) [1.1].
*   **Характер данных:** Событийные / Полуструктурированные (JSON-логи действий пользователей на экранах) [1.1].
*   **Целевое хранилище:** **Data Lakehouse** (Слой сырых файлов на S3) [1.1].
*   **Способ обработки:** Асинхронный, **Daily Batch** (Ночной сбор накопленных на фронт-серверах логов за сутки) [1.1].
*   **Потребители:** Департамент маркетинга, Продуктовые аналитики (CJM / Воронки продаж) [1.1].
*   **Архитектурная логика (Трансформация):** Проектирование опирается на принцип экономической целесообразности. Для бизнес-анализа воронки продаж real-time стриминг логов кликов не имеет практического смысла. Данные собираются раз в сутки ночью, в период падения нагрузки на инфраструктуру. Это защищает сеть от перегрузки и позволяет спокойно собирать целостную картину поведения клиентов для оптимизации шагов оформления продуктов [1.1].
