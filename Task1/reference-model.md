# Маппинг ключевых сущностей на референсную модель BIAN

Для унификации терминологии и проектирования целевых доменов данных (Data Products) после слияния FinUnion Group и RetailBank, ключевые бизнес-сущности сопоставлены с сервисной моделью стандарта BIAN (Banking Industry Architecture Network).

## 1. Таблица сопоставления сущностей с доменами BIAN

| Бизнес-сущность (из нашей ERD) | Сервисный домен BIAN (Service Domain) | Роль домена в целевой архитектуре |
| :--- | :--- | :--- |
| **Party Data Management (Единый ID)** | **Party Data Management** | Центральный реестр уникальных идентификаторов всех контрагентов объединенного банка. |
| **Клиент** | **Customer Registry / Party Lifecycle Management / Corporate Customer Agreement** | Управление анкетами, персональными данными и жизненным циклом физических лиц. / Управление реквизитами, структурой холдингов и связями юридических лиц. |
| **Сотрудник банка** | **Party Lifecycle Management (Internal)** | Учет внутренних участников процессов (персонала) для аудита и назначения ролей. |
| **Обращение клиента** | **Customer Case Management** | Регистрация, маршрутизация и ведение истории жалоб, претензий и запросов в CRM. |
| **Отделения** | **Business Direction / Branch Location** | Справочник физических точек присутствия и гео-привязки бизнеса. |
| **Договор (Соглашение)** | **Customer Agreement** | Юридическое оформление сделок, фиксация взаимных обязательств банка и клиента. |
| **Банковский продукт (Тариф)** | **Product Directory / Product Inventory** | Централизованный канонический каталог всех доступных и архивных тарифов и условий. |
| **Счёт** | **Current Account / Savings Account** | Ведение балансов, учет доступных остатков на расчетных и сберегательных счетах. |
| **Карта** | **Card Transaction Management** | Управление статусами пластиковых/вифровых карт, авторизациями и лимитами. |
| **Платёж (Бизнес-операция)** | **Payment Execution** | Инициирование, валидация и маршрутизация клиентских переводов (СБП, поручения). |
| **Транзакция (Проводка в АБС)** | **Bank Core Accounting** | Бухгалтерский учет операций, формирование двойной записи (дебет/кредит) в Главной книге. |

## 2. Архитектурное обоснование: как BIAN помогает при слиянии

Использование референсной модели BIAN в данном проекте решает 4 критические проблемы интеграции:

1. **Унификация терминологии:** В FinUnion использовалось понятие «Кредитное соглашение», а в интегрируемом банке — «Договор займа». Приведение данных к канонической сущности BIAN `Customer Agreement` на этапе загрузки в аналитическую платформу полностью стирает терминологические различия между мастером и ведомым банком.
2. **Определение границ владения данными (Data Ownership):** BIAN жестко разграничивает функционал. Например, домен `Card Transaction Management` отвечает только за операции по картам и не управляет балансом счета (это зона ответственности `Current Account`). Это позволяет четко закрепить за бизнес-лидерами объединенного банка владение конкретными доменами данных.
3. **Поиск пересечений между системами:** Маппинг наглядно подсвечивает дублирующие функции систем. Так, блоки `FU Cards` и `RB Cards` претендуют на один и тот же домен BIAN `Card Transaction Management`. Это служит явным маркером для ИТ-команды, какие системы необходимо объединить в первую очередь.
4. **Проектирование целевых доменов данных (Data Products):** На основе сервисных доменов BIAN формируется архитектура **Data Mesh**. Каждый домен (например, домен Кредитования на базе `Consumer Loan`) силами собственных инженеров выпускает наружу стандартизированные наборы данных (Data Products) через строгие инженерные контракты (Data Contracts), что исключает появление хаотичных связей «точка-точка» (Point-to-point), которые использовались ранее.
